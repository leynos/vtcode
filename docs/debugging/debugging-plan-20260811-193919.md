# ACP history and resume debugging plan

## Symptom

ACP turns appear not to create history, and sending another message does not
resume the previous session after an ACP process is replaced.

## Evidence gathered

- `[history]` is omitted from `~/.vtcode/vtcode.toml`, so the default file
  persistence policy applies.
- Current ACP processes were started after the installed VTCode binary was
  updated, ruling out an obviously stale executable.
- ACP checkpoints are being written successfully under
  `~/.config/vtcode/sessions/`, not `~/.vtcode/history/`.
- A newly spawned ACP process advertises a newly generated session identifier.
  Its debug log does not show an archived session being attached.

## Hypotheses

### H1: the ACP client starts a new session instead of loading the old session

Prediction: after replacement of an ACP process, the new process handles
`session/new`, produces a new UUID, and never handles `session/load` for the
prior UUID. The prior archive remains intact.

Test: add or use bounded RPC lifecycle logging, then compare the first session
request and identifier in consecutive ACP process logs. This hypothesis is
falsified if the replacement process receives `session/load` with the archived
identifier.

### H2: VTCode receives `session/load` but fails to reconstruct the thread

Prediction: a direct load of a persisted archive either errors or produces a
thread whose restored message list differs from the archive.

Test: persist a session, construct a fresh `ZedAgent`, call `load_session` with
the archived identifier, and assert the restored messages are present in
`resolved_messages`. This hypothesis is falsified if the fresh agent restores
the exact messages.

### H3: ordinary failed turns are not checkpointed at the failure boundary

Prediction: when provider execution fails after a user prompt is accepted, the
archive ends before that prompt or partial assistant response, leaving nothing
useful for a later load.

Test: inject a deterministic provider failure into the prompt handler and
inspect the persisted checkpoint. This hypothesis is falsified if the accepted
prompt and incomplete assistant response are both present.

### H4: VTCode omits the current ACP discovery and resume methods

Prediction: VTCode's ACP dispatcher registers legacy `session/load` but not
`session/list` or `session/resume`, and initialization advertises only the
legacy `loadSession` flag rather than `sessionCapabilities.list` and
`sessionCapabilities.resume`.

Test: inspect the request-dispatch builder and initialization response against
the request and capability types provided by the pinned
`agent-client-protocol` crate. This hypothesis is falsified if both methods are
registered and both capabilities are advertised.

Verdict: not falsified. `install_handlers` registers `session/load` only, and
`handle_initialize` sets only the legacy `loadSession` flag. The pinned ACP
crate defines `session/list`, `session/resume`, and their corresponding
`sessionCapabilities` markers.

## Selected correction

Keep legacy `session/load` compatibility, and add the current discovery and
resume surface:

- advertise `sessionCapabilities.list` and `sessionCapabilities.resume`;
- implement paginated, optionally workspace-filtered `session/list` from the
  durable archive store;
- implement `session/resume` by attaching the exact requested archive ID;
- share the attach/configuration path with legacy `session/load`; and
- add request-dispatch, capability, listing, and fresh-runtime resume tests.

## Implementation outcome

- Durable checkpoints were already being written successfully to the resolved
  configuration directory's `sessions/` store. No ACP process was writing to
  `~/.vtcode/history/` because that path is not the durable archive store.
- ACP now advertises `sessionCapabilities.list` and
  `sessionCapabilities.resume` while retaining `loadSession` compatibility.
- `session/list` returns recent archives in pages of 100, optionally filtered
  by exact normalized workspace, with opaque offset cursors.
- `session/resume` attaches the exact requested archive and rejects
  cross-workspace restores. It does not guess the latest session, which would
  be ambiguous when several ACP agents share a workspace.
- Debug logging now distinguishes creation, listing, legacy loading, and
  current resume operations without logging message contents.

Focused validation: all 149 `vtcode-acp` unit tests passed, including new
coverage for advertised capabilities, workspace filtering, pagination, resume,
and cross-workspace rejection.

## Decision rule

Fix the lowest boundary proven faulty. Do not infer a prior session for an
ambiguous `session/new` request when several ACP sessions may share a workspace;
resume must remain keyed by the ACP session identifier unless the protocol
provides an unambiguous recovery token.
