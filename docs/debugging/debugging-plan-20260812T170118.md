## Problem Statement

ACP turns still leave `~/.vtcode/history` and `~/.vtcode/audit` empty. After an
Arli network failure, submitting a follow-up such as `please continue` appears
to do nothing. Two recent sessions ended with a request-level network error for
`https://api.arliai.com/v1/chat/completions` despite the configured retry
policy.

## Current Evidence

- Four currently running ACP processes use the rebuilt binary and the Arli
  custom-provider profile.
- Durable session archives are actively updated under
  `~/.config/vtcode/sessions`; persistence is therefore not globally broken.
- The active configuration contains neither `[history]` nor `[acp.audit]`, so
  audit is disabled and history uses defaults.
- Terminal provider failures in `run_prompt` are returned as JSON-RPC errors.
- The populated Git fixture at
  `/home/leynos/Projects/vtcode-arli-toolcall-fixture` has already elicited real
  Arli tool calls and is suitable for an ACP replay matrix.

## Hypotheses

### H1: Terminal provider errors poison the client-visible ACP turn

**Claim**: Returning an ACP JSON-RPC error after retry exhaustion causes the
editor to treat the prompt, or its agent process, as terminal. The in-memory
session can technically accept another prompt, but the client never obtains a
normal stopped-turn response from which it can continue.

**Prediction**: In a duplex ACP test backed by a deterministic failing provider,
the first `session/prompt` returns an RPC error. A second prompt is not a
protocol-level continuation of a completed turn. If the failure is instead
reported as an agent message followed by a normal stop response, the same
session accepts and completes a second prompt.

#### H1 Falsification Plan

1. Use the smallest existing SACP duplex harness and a provider double that
   fails once before succeeding.
2. Submit two prompts against the same session.
3. Record the first request's wire result and whether the second reaches the
   provider.

**Expected negative result**: The first prompt already returns a normal
`PromptResponse` and the second reaches the provider, disproving the claim.

### H2: `[history].persistence` was wired only to session archives

**Claim**: ACP checks the history persistence switch when writing durable
session archives but never invokes the history-file writer that owns
`~/.vtcode/history`, so the visible history store remains empty by design.

**Prediction**: References from the config type reach `session_archive` but no
ACP prompt path reaches `HistoryFileManager`.

**Expected negative result**: A prompt checkpoint calls the history-file writer
with the ACP session identifier, disproving the claim.

### H3: Audit is empty because its explicit opt-in is absent

**Claim**: The ACP audit implementation is correct, but the live config does
not enable `[acp.audit]`.

**Prediction**: `AcpAuditLogger::from_config` returns `None` for the current
configuration; enabling the documented option creates and appends to the
configured log during a fixture tool call.

**Expected negative result**: The logger is enabled under the current config or
still fails to append after explicit enablement.

## Falsification Result

H1 was **not falsified**, with medium confidence. The focused
`bad_gateway_retries_until_the_configured_budget_is_exhausted` test confirms
that retry exhaustion is deterministic, and
`failed_turn_releases_session_and_preserves_gathered_context` confirms that the
turn marker is released while gathered context remains available. At the
handler boundary, `ProviderCallError::Failed` becomes
`SdkError::internal_error`, which is passed directly to the SACP responder.

This establishes that session state survives while the client receives a
request error. It does not yet prove the editor's reaction because the current
test suite has no prompt-level duplex test that sends a second
`session/prompt` on the same connection. The implementation must add that
missing wire-level regression before changing the error mapping.
