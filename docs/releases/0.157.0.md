# Diapason 0.157.0

## Configuration and migration

Newly added configuration fields have defaults and require no mandatory edits
to existing configuration files. Set them only when you want to override their
defaults.

One existing setting now has a stricter requirement: ACP tool rounds need a
durable session checkpoint, so a configuration with
`[history].persistence = "none"` must set `[history].persistence = "file"`
before ACP tool rounds can run. A prompt that requests tools otherwise fails
with a checkpoint error before any tool executes, so no tool side effects
occur. See [ACP behavior](#acp-behavior) and
[ACP session storage](../guides/zed-acp.md#storage-boundaries).

## Breaking API renames

Diapason now uses British spelling for colour-related identifiers. The rename
is mechanical: `color` becomes `colour`, `Color` becomes `Colour`, `Center`
becomes `Centre`, and `Colorizer` becomes `Colourizer`. The old spellings are
removed rather than deprecated, so downstream Rust callers must update to the
new names.

The command-line flag is now `--no-colour`. The previous `--no-color` spelling
remains available as a visible alias, so existing scripts keep working.

Configuration keys keep their canonical American spelling on the wire:
`ui.color_scheme_mode` and `ui.safe_colors_only` are still the serialized
names. The British spellings `ui.colour_scheme_mode` and `ui.safe_colours_only`
are accepted as aliases when reading configuration. Specifying both spellings
of the same field in one table is a duplicate-field error.

Compatibility is preserved where the spelling is external:

- Configuration keys, wire protocol fields and telemetry metric names keep
  their canonical `catalog` spelling. Only the Rust API is renamed.
- The pod store keeps reading and writing `catalog.json`, even though the
  accessor is now `PodsStore::catalogue_path()`. Existing installations keep
  their customized deployment profiles without migration.
- The embedded default catalogue asset is renamed to
  `default_catalogue.json`; it is compiled into the binary and creates no
  on-disk migration.
- Runtime prompt metadata now uses the `[Runtime Tool Catalogue]` header.
  Refreshing a prompt removes the legacy `[Runtime Tool Catalog]` section but
  preserves runtime notices appended after it, and the stable-prefix hash
  ignores metadata under either header.
- Rendered report labels use the British spelling too. The
  `diapason trajectory` report prints `tool_catalogue` in its cache-churn rows
  and titles its order section `Tool Catalogue Order`. The shared session
  timeline reports `tool_catalogue` among its cache-churn counts. Trajectory
  records keep their existing `tool_catalog_cache_metrics` kind and
  `tool_catalog` change reason, so archived logs and log consumers are
  unaffected.
- `ThreadEvent` keeps its `previous_catalog_hash` and `new_catalog_hash` fields
  because they are part of the serialized event contract. The internal segment
  transition that feeds them is
  `RequestSegmentTransition::previous_catalogue_hash`.

Crate-private items are renamed in place and have no migration entry: fields
and helpers on `pub(crate)` or `pub(super)` types are not nameable by a
downstream crate. That covers `PromptCacheDiagnostics` (including
`tool_catalogue_changes` and `last_tool_catalogue_hash`),
`RequestSegmentTransition`, the `pub(super)` accessor `ToolAssembly::catalogue`,
`ToolCatalogCacheMetrics`, `ToolCatalogState`, `PrimaryAgentCatalogue` and the
internal `pub` fields of the `diapason` binary's context structs.

## Breaking Rust API changes

Two public structs gained a required field. Both new fields are
`#[serde(default)]`, so previously serialized payloads still deserialize; only
Rust struct literals must change.

| Type                 | New field                                      | Migration                                                                                                                                |
| -------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `MetricsSummary`     | `tool_recovery: ToolRecoveryMetrics`           | Set it from `MetricsCollector::get_tool_recovery_metrics()`, or use `ToolRecoveryMetrics::default()` when building a summary by hand.    |
| `ToolExecutionError` | `stale_exec_session: Option<StaleExecSession>` | Add `stale_exec_session: None` to struct literals. Prefer `ToolExecutionError::from_anyhow` and `from_error_payload`, which populate it. |

Recovery counters are available from
`diapason_core::metrics::{ToolRecoveryEvent, ToolRecoveryMetrics}` and are
exported as `diapason_tool_recovery_total{event="…"}` in Prometheus and as
`tool_recovery` in the JSON summary. See
[recovery metrics](../users-guide.md#recovery-metrics).

## New Rust API

- `ThreadRuntimeHandle::mutate_messages` applies a short, synchronous callback
  while the thread's session lock is held, so callers can stage or replace tool
  results atomically without a second lock. The callback must not call back
  into the handle, await, or perform I/O while the lock is held.
- `ToolRegistry::set_metrics_collector` installs a collector on one registry
  instance. Components that cloned the previous collector at construction keep
  it, while execution paths that read `ToolRegistry::metrics_collector()`
  observe the replacement, so install the shared collector while the registry
  is built.
- `SessionArchive::prepare_checkpoint_snapshot` and
  `SessionArchive::write_prepared_checkpoint_async` split a checkpoint into a
  compaction step and a write step, so a caller can reject a payload before it
  replaces the archive on disk. `prepare_checkpoint_snapshot` returns `None`
  when history persistence is disabled. See
  [checkpoint preparation](../users-guide.md#checkpoint-preparation-api).

## ACP behavior

- Each ACP session validates the absolute workspace selected by the client;
  an invalid workspace is rejected instead of falling back to the server's
  launch directory. See the [Zed ACP guide](../guides/zed-acp.md).
- Durable session archives support discovery, loading and resuming when history
  persistence is enabled. See
  [ACP session storage](../guides/zed-acp.md#storage-boundaries).
- ACP tool rounds require a durable session checkpoint before execution. With
  `[history].persistence = "none"`, a prompt that requests tools fails with a
  checkpoint error before any tool runs, so no tool side effects occur. Enable
  durable history, for example `history.persistence = "file"`, to use ACP tool
  rounds.
- Custom-provider requests use bounded retries and separate deadlines. Failures
  before visible output may be retried; after output begins, partial responses
  are preserved as incomplete and are not replayed. See the
  [custom-provider request policy](../development/CUSTOM_PROVIDER_REQUEST_POLICY.md).
- ACP clients receive best-effort `_diapason/taskLifecycle` notifications for
  sub-agent and background-process progress and terminal status changes. See
  [task lifecycle notifications](../guides/zed-acp.md#runtime-behaviour).
- An interrupted ACP tool round is recovered rather than replayed. The call is
  given one incomplete terminal result and is not executed again; a successful
  round replaces the staged result with the real one. See
  [interrupted tool recovery](../development/acp-runtime.md#interrupted-tool-recovery).
- Legacy session archives are repaired when an unresolved tool call has an
  unambiguous outcome. Ambiguous history is rejected without rewriting the
  archive, so a session is never resumed from a guess. See
  [archive repair](../development/acp-runtime.md#interrupted-tool-recovery).
- A best-effort checkpoint that compaction would strip of write-ahead evidence
  is skipped rather than written, leaving the previous archive intact and
  keeping the tool call protected. The skip is reported as the
  `checkpoint_skipped` recovery event with a `degraded` storage outcome, not as
  a failure. Checkpoint failures report a bounded category such as
  `archive_write_failed` instead of a raw error chain that could name archive
  paths.

## Tool safety

- `read_file` returns a `content_hash` describing the content the model actually
  received, whenever that content can be certified against the bytes on disk; a
  truncated response, a diverging unsaved buffer, or append-only output that
  grows mid-read returns no hash instead. `apply_patch` accepts a returned hash
  back as `expected_content_hash`. When the caller supplies that hash, a patch
  written against older content is rejected before any file is touched;
  unversioned patches are unaffected. See the
  [patch safety guide](../guides/patch-safety.md).
- A patch that leaves every touched file byte-identical is reported as a no-op
  rather than applied silently, and the third identical repeat is refused. This
  replaces the previous behaviour where a no-op patch was accepted indefinitely.
- A `write_stdin` continuation for a process-local exec-session identifier that
  has already terminated returns a non-retryable `ResourceNotFound` error with
  `details.reason: "stale_exec_session"`. Start a new `exec_command` and use
  the returned session ID. When `details.input_delivered` is `true`, the input
  was written before the session was lost, so verify whether partial state
  exists before retrying the work. See
  [stale exec sessions](../users-guide.md#stale-write_stdin-sessions).
