Vendored syntect
================

Upstream crate: syntect 5.3.0
Upstream repository: https://github.com/trishume/syntect
Archive verified: https://static.crates.io/crates/syntect/syntect-5.3.0.crate
Archive SHA-256: 656b45c05d95a5704399aeef6bd0ddec7b2b3531b7c9e900abbf7c4d2190c925
Upstream commit: e4670846ecf16d8832db6c43d531bec466214e27
Licence: MIT (LICENSE.txt, retained unmodified)

Why this exists
---------------

syntect 5.3.0 encodes its bundled `.packdump` and `.themedump` assets with
`bincode 1.3.3`, which is unmaintained (RUSTSEC-2025-0141). Upstream PR
https://github.com/trishume/syntect/pull/694 replaces that codec, but it is
unmerged, and no published syntect release removes the advisory. Rather than
suppress the advisory or regenerate the assets, this tree keeps syntect 5.3.0
byte-for-byte and changes only the codec.

What changed relative to the published archive
----------------------------------------------

1. `Cargo.toml`
   - The normalized-manifest banner is replaced by a note pointing here.
   - The optional dependency `bincode = "1.0"` becomes
     `bincode = { package = "bincode-next", version = "=3.1.2",
     default-features = false, features = ["serde", "std"] }`. The dependency
     is still renamed to `bincode`, so syntect's feature graph
     (`dump-create`, `dump-load`) is unchanged.
   - Example, test, and bench targets and their development-only dependencies
     are dropped. They are not part of the library and reference upstream's
     `testdata/` tree, which the crates.io archive excludes.
   - The packaged `[profile.dev.package.*]` overrides are dropped; a patched
     path dependency cannot contribute profile settings, and Diapason's own
     profile governs.

2. `src/dumps.rs`
   - `bincode::serialize_into`/`deserialize_from` are replaced by
     `bincode_next::serde::encode_into_std_write`/`decode_from_std_read`,
     both configured with `bincode_next::config::legacy()`.
   - The `bincode::Result` alias is replaced by a local `DumpError` enum that
     unifies IO and codec failures and is `#[non_exhaustive]`. This is a
     semver-visible change for anyone matching on the previous `bincode::Error`,
     and a deliberate one: exposing a bincode type in the public API is what
     kept this crate tied to the unmaintained codec.
   - `from_binary` keeps its panic-on-invalid contract and now reports the
     underlying error instead of unwrapping a bare `bincode::Error`.

Nothing else in `src/` or `assets/` differs from the published archive. No
`#[allow(...)]` attribute was added.

Wire compatibility
------------------

`bincode_next::config::legacy()` is little-endian, fixed-int, no limit, no bit
packing, fingerprint disabled, and uses the `BincodeLegacyFormat` internal
format. It therefore reproduces bincode 1.3's `DefaultOptions`-with-fixint
encoding, including `allow_trailing_bytes` on decode.

Verified before the patch was adopted, by decoding each bundled asset with this
tree and re-encoding it in both formats:

- `default_newlines.packdump` and `default_nonewlines.packdump`: re-encode to
  identical bytes with both stock bincode 1.3.3 and this codec.
- `default.themedump`: zlib payload and full compressed dump both re-encode
  identically.
- Every one of the 75 bundled grammars highlights a sample line, which forces
  its nested `serialized_lazy_contexts` blob through the new codec.
- A truncated dump fails to decode, confirming the round-trip checks are not
  vacuous.
- A primitive-encoding comparison (integers, strings, `Vec`s, `Option`, tuples,
  maps) is byte-identical between the two codecs.

Exiting this patch
------------------

Delete this directory and the `syntect` entry in the root
`[patch.crates-io]` table as soon as a published syntect release replaces the
codec. Then narrow nothing else: the `diapason-ui` feature list is independent
of this patch and stays as it is.
